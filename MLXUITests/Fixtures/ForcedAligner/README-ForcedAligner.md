`repo-files-ForcedAligner.json` is the repository's file list at the pinned revision, fetched through the Hugging Face
API (`?blobs=true`, 2026-11-19). `ForcedAlignerCatalogTests` pins that `ModelFileSelector` downloads nine of them,

pick them for any repository that has them. The repository has no `tokenizer.json`: the library writes one into the
model folder on first load and the tokenizer loader reads that.

`preprocessor_config.json`: the pinned aligner (mlx-audio-swift @ `5c4c12b`) does **not** read it. `preprocessAudio`
in `Qwen3ForcedAligner.swift` hard-codes 16 kHz, nFft 400 and hop 160, and takes the mel-bin count from `config.json`.
The existing `metadataNames` rule in `ModelFileSelector.swift` still downloads it. This differs from issue #13 trap 2,
which lists it among the files the loader reads.

  scope here. Change the file-list test's comment to say the pinned aligner doesn't read the file and the existing

The fixture files keep unique basenames (`README-ForcedAligner.md`, `repo-files-ForcedAligner.json`,
`golden-ForcedAligner.json`) because `MLXUITests` is an Xcode synchronized group that flattens resources by basename.

## Units and gotchas

- Times are **seconds**, in transcript order, rounded to three decimals by the reference itself. The reference does not clip times to the audio duration; the engine's contract (issue decision 4) does.
- One unit is one word for space-separated languages and one CJK character for Chinese, in both the Python and Swift splitter. Punctuation is dropped by the splitter, so `items` never contains it. Japanese differs -- see the next bullet.
- **Japanese is aligned with `language="Japanese"`, the name the Swift engine passes, and the two runners split it differently.** Python takes its nagisa path and times `こんにちは、世界。` as `["こんにちは", "世界"]`. The pinned Swift runner has no Japanese tokenizer (`Qwen3ForcedAligner.swift` @ `5c4c12b`, `encodeTimestamp`: every language but Chinese goes to `tokenizeSpaceLang`) and gives `["こんにちは", "世", "界"]`. In the parity test only, for Japanese only, consecutive Swift units whose text exactly makes one reference unit are joined before the ±80 ms comparison; a join that does not line up fails. The engine and the app keep the library's split (issue #13 decision 4), and `ForcedAlignerEngineTests` pins it. The difference is reported upstream, with the Chinese drift (owner ruling 2), in [mlx-audio-swift issue 422](https://github.com/Neywa-Labs/mlx-audio-swift/issues/422).
  - Owner ruling 1 (Boo, 2026-11-27): "Accept it only if it matches the language name the Swift engine passes. Regenerate the Japanese golden with the library's full name for Japanese. If the units and times are identical, keep it and note that in the fixture README. If they differ, the golden uses the same name Swift passes."
  - Owner ruling 8 (Boo, 2026-11-27): "Option A. Use the 'Japanese' golden. In the parity test only, for Japanese only, join consecutive Swift units whose concatenated text exactly equals one reference unit, then apply ±80 ms to the joined span. If the join doesn't line up exactly, the test fails. The engine and the app's output stay as the library splits them (issue #13 decision 4: don't re-split). Add a test that pins Swift's current Japanese units (こんにちは, 世, 界), so a future upstream splitter shows up as a deliberate change. Note the difference in the fixture README, and add it to the same upstream mlx-audio-swift report as the Chinese drift (ruling 2). Chinese stays as ruling 2: exact units, ±160 ms."
- Audio is read with the stdlib `wave` module and passed as a float32 array. `python3 -I` hides the user site-packages, so the package's miniaudio/cffi WAV loader raises `ModuleNotFoundError: _cffi_backend` if used; passing samples avoids it.
- The checkpoint's model card example (both CLI and Python) omits the transcript; for the aligner the transcript is mandatory, so that example fails. Always pass `--text` / `text=`.
